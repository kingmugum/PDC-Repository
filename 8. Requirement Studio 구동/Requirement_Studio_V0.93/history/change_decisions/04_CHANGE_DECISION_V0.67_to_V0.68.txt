Requirement Studio V0.67 -> V0.68 Change Decision
===================================================
Date: 2026-10-02
Decision: HARDEN AUTOMATED EVALUATION PERSISTENCE / REMOVE EXTERNAL GOLD STORE CREATION
Requirements baseline: Requirement_Studio_Requirements_Management_rev55.xlsx (UNCHANGED)

1. Why V0.68
-------------
A real V0.66/V0.67 run showed that `automatic_evaluation/` could appear empty while the three reviewers were executing because provider artifacts were persisted only after all concurrent reviewers finished. A V0.66 run also logged evaluation completion although the user could not find files in the expected folder; the prior completion path did not re-open and verify all user-visible files before emitting the completion log.

Separately, `GoldSourceRegistry` created a sibling directory named `Requirement_Studio_Gold_Sources` outside the Requirement Studio package. The user requested that no such external sibling folder be created; normal document operation will continue to use the package `input/` folder.

2. Automated evaluation persistence fix
--------------------------------------
- `automatic_evaluation/00_EVALUATION_STATUS.json` and `.txt` are created immediately.
- `06_EVALUATION_EVIDENCE.json` is now stored inside `automatic_evaluation/`.
- GPT/Gemini/Claude JSON/TXT are persisted immediately as each reviewer completes rather than waiting for all three.
- File publication uses temporary-file + flush/fsync + atomic replace.
- `99_EVALUATION_COMPLETE.ok` is created only after final on-disk verification.
- UI completion logging includes verified file count and final_result part count.
- Evaluation failure logging points directly to `00_EVALUATION_STATUS.txt`.
- If the result contract is incomplete or zero-size, evaluation raises an error instead of logging a false completion.

3. Gold Source storage cleanup
------------------------------
- V0.68 no longer creates `<parent>/Requirement_Studio_Gold_Sources`.
- User-registered compact Gold contracts, when the existing optional Gold registration feature is used, are stored inside:
  `review_exchange/gold_sources/user_registered/`
- If the exact legacy external program-owned layout exists, V0.68 migrates known registry/contracts into the internal store and removes the obsolete sibling directory.
- Unexpected files in the legacy folder are never deleted automatically.
- The Gold/Regression feature itself is retained because it is already part of the approved rev55 requirements baseline. No requirement is changed for this storage-location cleanup.

4. Requirements governance
--------------------------
`Requirement_Studio_Requirements_Management_rev55.xlsx` is copied byte-for-byte from V0.67. No requirement row, acceptance criterion, failure scenario, lock, regression item, code-evidence row, AI rule, or conflict-review row is modified in V0.68.

Compatibility review:
- FR-316 / FR-362~FR-365 remain satisfied: auto/manual/none evaluation modes and transmission boundary are unchanged.
- FR-339 Gold Source import remains supported; only its physical persistence location changes from an external sibling store to an internal review_exchange store.
- LOCK-003 remains satisfied: external AI transmission occurs only in the explicitly approved automatic evaluation mode.
- No conflict with input-file protection or Source-of-Truth rules is introduced.

5. Release validation
---------------------
- V0.68 regression tests include an in-progress persistence test proving the automatic_evaluation folder is non-empty before reviewers finish.
- Reviewer result files are checked after generation.
- Gold registry tests prove that constructing/registering a Gold Source does not create the external sibling directory.
- Legacy external Gold layout migration is tested.
- Full Python regression and compile checks must pass before packaging.
