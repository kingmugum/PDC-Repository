PassFail rev87 - Stimulus 단계별 자동진단 안내
==================================================

1. rev87에서 추가한 이유
- rev69에서 `CAPL 호출 frames=4`, target Message `Tx=0 / Rx=11`, Active 값 미관측인 사례가 확인되었습니다.
- target Tx=0만으로는 실제 송신 실패인지, CANoe Logging이 Tx를 기록하지 않는 구성인지 구분할 수 없습니다.
- 따라서 rev87은 단순 로그 표시가 아니라 '어디까지 확인됐고 다음에 무엇을 봐야 하는지'를 단계별로 분리합니다.

2. 자동진단 단계
[AUTO-DIAG][1/CALL]
- Python/PassFail -> CAPL/Stimulus 호출이 수행됐는지 확인합니다.
- 이 단계 성공은 실제 버스 TX 성공과 동일하지 않습니다.

[AUTO-DIAG][2/LOGGER]
- ASC 전체와 선택 CAN의 Tx/Rx 개수를 먼저 확인합니다.
- ASC 전체 Tx=0이면 현재 Logging이 Rx-only일 수 있으므로 target Tx=0을 실제 송신 실패로 단정하지 않습니다.
- ASC에는 다른 Tx가 있는데 선택 CAN 또는 target Message만 Tx=0이면 SEND branch/논리 CAN/Bridge 경로를 우선 확인합니다.

[AUTO-DIAG][3/TARGET]
- 이번 Stimulus 실행 시간창에서 target Message 자체가 몇 frame 보였는지 확인합니다.

[AUTO-DIAG][4/ACTIVE]
- 목표 Active 값(예: DPSS_StSldFwdMvBtn=2)이 실제 로그에 있었는지 확인합니다.

[AUTO-DIAG][5/SOURCE]
- 같은 Message ID의 Rx가 Stimulus 시간창에 계속 존재하는지 확인합니다.
- 사용자가 '기존 송신원 분리·비활성 확인'을 체크했는데도 Rx가 계속 보이면 원 ECU/Generator가 실제로 살아 있거나 CANoe 방향 기록 방식이 예상과 다를 수 있으므로 재확인합니다.
- 이 결과만으로 기존 ECU 미분리를 자동 확정하지는 않습니다.

[AUTO-DIAG][6/INTENDED-E2E]
- PassFail이 실제로 만들려고 한 baseline/active raw payload를 비교합니다.
- target Signal이 바뀌었는데 CRC/Alive/Counter가 그대로라면 '정적 유지'로 표시합니다.
- rev87은 CRC/Alive/E2E 알고리즘을 추측하거나 자동 계산하지 않습니다.

[LOG-VERIFY][TC-OUTPUT]
- 선택한 TC와 연결된 output_conditions를 CAN1~CAN3 OR 후보로 확인합니다.
- input Active가 로그에 잡힌 뒤 Expected output이 관측됐는지를 별도로 표시합니다.
- 네트워크 output 반응이 있어도 실제 시트 움직임 PASS로 자동 판정하지 않습니다.

3. 실행 시간창
- CAPL backend는 실제 Stimulus 직전에 Measurement를 restart하므로 기본적으로 0초~Hold+여유시간만 분석합니다.
- 이렇게 해서 같은 로그 안의 이전/이후 unrelated frame이 Active/원복으로 잘못 섞이는 문제를 줄였습니다.
- 다른 backend에서는 ASC date header + wall-clock을 best-effort로 맞추고, 불가능할 때만 전체 로그 fallback을 사용하며 mode를 화면에 표시합니다.

4. 현재 사례에서 rev87이 기대하는 출력
현재와 같은:
  CAPL calls=4
  PSS... target window Rx=11, Tx=0
  Active=2 미관측
  ASC 전체 Tx=0
이라면 다음과 비슷하게 나와야 합니다.

  [AUTO-DIAG][2/LOGGER] ASC 전체 Tx 레코드 0 -> Tx Logging 설정 확인 필요
  [AUTO-DIAG][4/ACTIVE] Active=2 로그 관측=NO
  [AUTO-DIAG][5/SOURCE] 동일 ID Rx 지속
  [AUTO-DIAG][6/INTENDED-E2E] Alive/CRC baseline과 동일(정적 유지)
  [AUTO-DIAG][VERDICT] Tx Logging 설정 확인 후 재검증
  [AUTO-DIAG][NEXT] Logging -> Bridge/논리 CAN -> CRC/Alive/E2E -> ECU/물리 조건 순으로 확인

5. 이 버전에서 '더 필요한 것'
- 지금 단계의 원인 분리에는 위 진단이면 충분합니다.
- CRC/Alive/E2E를 실제로 올바르게 생성하는 기능은 진단과 별개의 다음 개발 단계입니다.
  CRC polynomial, init/xor, Data ID, counter 규칙, 보호 범위 등을 확인하지 않고 임의로 계산하지 않습니다.
- 실제 차량 기능까지 자동 PASS로 판단하려면 로그상의 TC output 반응 외에 실제 seat/motor feedback 등 물리 증거가 별도로 필요합니다.

6. 기존 기능 영향
- 단일/다중 TC FinalCheckResult 및 기존 Rx-only 로그 재검토는 변경하지 않습니다.
- Stimulus 로그 자동진단은 TX/RX 디버깅 전용입니다.
- 자동진단 결과가 Stimulus ok/restore_ok나 단일/다중 PASS/FAIL을 뒤집지 않습니다.
