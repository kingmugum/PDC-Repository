PassFail rev85 - 단일 TC 수행 완료 후 로그 재검토 지연 수정
============================================================

[현상]
- CANalyzer/CANoe에서 단일 TC Start 후 수행 완료를 누르면 실시간 읽기 결과는 미관측으로 마감되지만,
  로그 확인 단계가 30초 이상 진행되지 않는 것처럼 보일 수 있음.

[원인]
- rev56 단일 TC 최종 판정 경로는 입력/출력 기대 Signal 하나마다 로그를 처음부터 다시 검토함.
- BLF 사용 시 각 기대조건마다 BLF -> ASC 변환까지 반복될 수 있어, 로그가 크거나 기대조건이 여러 개면 시간이 크게 증가함.
- 로그 처리 중 GUI 단계 표시가 없어 사용자는 멈춘 것으로 인식하기 쉬움.

[rev85 수정]
1. 단일 TC도 기존 다중 TC용 review_conditions_in_log_batch([condition]) 엔진을 사용.
2. 선택 로그를 한 번 준비하고, 해당 TC의 모든 입력/출력 기대조건을 한 번의 ASC 순회로 동시에 판정.
3. 수행 완료 후 GUI에 다음 단계 로그를 표시.
   - [LOG] 로그 파일 탐색/안정화 단계 시작
   - [LOG] 로그 재검토 시작: <file> (단일 TC 1회 스캔)
   - [LOG] 로그 일괄 재검토 완료: 1개 TC
4. 상태 박스는 처리 중 '로그 확인중'으로 표시.
5. 4분할 요약의 'CANoe 읽기' 문구를 'Vector 실시간 읽기'로 변경해 CANalyzer에서도 자연스럽게 표시.

[판정 정책]
- 실시간 PASS 우선 정책은 변경하지 않음.
- 수행 완료(done_event)와 중단(stop_event)의 의미는 변경하지 않음.
- DBC 오류와 기능 FAIL 구분도 유지.
- 로그가 매우 큰 경우 1회 스캔 자체의 시간은 필요할 수 있으나, Signal 수만큼 같은 로그를 반복 스캔하지 않음.

[현장 재확인]
- CANalyzer 9.0 SP1 연결
- 단일 TC Start
- 수행 완료
- '로그 확인중' 및 [LOG] 메시지 확인
- 최종 PASS/FAIL/ERROR가 정상 종료되는지 확인

[rev85 추가 수정 - 빈 로그/미관측 Actual 표시]
- 로그 파일을 정상적으로 찾고 재검토까지 완료했지만 대상 Signal이 한 번도 관측되지 않은 경우:
  * 입력 - 로그 확인: Actual = 미관측, Status = FAIL
  * 출력 - 로그 확인: Actual = 미관측, Status = FAIL
- 다음 경우에는 미관측으로 오표시하지 않고 기존 '-'를 유지:
  * 로그 결과 자체가 없음
  * DBC/Message 매핑 오류(ERROR)
  * 사용자 중단(N/A)
- 즉 '미관측'은 정상 로그 스캔이 수행된 기능 FAIL 의미로만 사용함.
